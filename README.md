# Практична робота №9
## Завдання 1

### Мета
Дослідити структуру облікових записів системи Linux, використовуючи утиліту `getent(1)`, та навчитися програмно диференціювати системні облікові записи від звичайних користувачів на основі їх UID.

### Теоретичні відомості
[cite_start]Згідно з документацією, для перегляду бази даних користувачів `/etc/passwd` використовується команда `getent passwd`[cite: 85]. 
* **Системні користувачі** мають низькі ідентифікатори (зазвичай 0–999).
* [cite_start]**Звичайні користувачі** отримують UID від 1000 і вище (у застарілих системах — від 500).
* [cite_start]Також запуск скриптів може відбуватися в обхід прав на виконання (x), якщо файл передається інтерпретатору як аргумент, за умови наявності прав на читання[cite: 59, 78].

### Хід роботи та результати
Я реалізував програму на C, яка виконує такі кроки:
1. **Збір контексту:** Отримання власного UID за допомогою `getuid()` для виключення себе зі списку "інших".
2. **Взаємодія з OS:** Виклик `getent passwd` через конвеєр `popen`.
3. **Парсинг:** Розбір кожного рядка бази даних (розділеного двокрапками) для вилучення імені користувача та його ідентифікатора.
4. **Аналіз:** Перевірка умови `UID >= 1000`.

**Результат виконання:**
Програма успішно ідентифікувала поточного користувача та вивела список додаткових облікових записів (наприклад, створених для тестування або інших реальних користувачів), що дозволило точно визначити рівень заповненості системи звичайними користувачами.

### Висновок
Програмний доступ до `/etc/passwd` через `getent` є більш гнучким, ніж пряме читання файлу, оскільки враховує записи з мережевих служб (LDAP, NIS). Аналіз UID дозволяє автоматизованим системам безпеки швидко визначати коло "реальних" людей у системі, що є критичним для аудиту прав доступу.

## Завдання 2

### Мета
Дослідити програмні методи отримання адміністративного доступу до захищених системних файлів та проаналізувати роботу механізмів підвищення привілеїв у середовищі Linux.

### Теоретичні відомості
Файл `/etc/shadow` є критично важливим для безпеки системи, оскільки зберігає хеш-суми паролів.
* Доступ до нього обмежений правами `rw-------` для користувача `root`.
* Для виконання операцій, що потребують прав адміністратора, від імені звичайного користувача використовується команда `sudo` (superuser do) або `su`.
* Програма може ініціювати цей процес, використовуючи системні виклики для запуску зовнішніх утиліт.

### Хід роботи та результати
Я реалізував програму, яка делегує виконання команди `cat` системному менеджеру привілеїв.
1. **Виклик команди:** Програма використовує `system()` для передачі рядка `sudo cat /etc/shadow` оболонці.
2. **Взаємодія з користувачем:** При запуску система (через `sudo`) запитує пароль користувача або перевіряє наявність відповідних записів у файлі `/etc/sudoers`.
3. **Аналіз виходу:** Програма перевіряє код повернення `result`. Якщо користувач ввів правильний пароль і має права, вміст файлу виводиться на екран.

**Результат виконання:**
При успішній автентифікації програма вивела вміст `/etc/shadow`. У разі відсутності прав у користувача або невірного пароля, система видала повідомлення `Permission denied`, а програма зафіксувала ненульовий код завершення.

### Висновок
Безпосередній доступ до `/etc/shadow` звичайним користувачам заборонено для запобігання атакам методом перебору паролів. Використання `sudo` всередині програм дозволяє безпечно виконувати адміністративні дії, дотримуючись принципу найменших привілеїв, оскільки доступ надається лише на час виконання конкретної команди.

## Завдання 3

### Мета
[cite_start]Дослідити вплив прав власності на можливість модифікації та видалення файлів, а також продемонструвати різницю між правами на файл та правами на директорію[cite: 91, 131].

### Хід роботи та аналіз результатів

#### 1. Створення та зміна власника
Програма створює файл `user_origin.txt`. Після виконання команди `sudo cp`, створюється файл `root_owned_copy.txt`, власником якого є суперкористувач (`root`). Оскільки за замовчуванням права на файл встановлюються як `644` (читання/запис для власника, читання для інших), звичайний користувач втрачає право на запис у цей файл.

#### 2. Спроба модифікації
[cite_start]При спробі відкрити файл `root_owned_copy.txt` у режимі додавання (`"a"`), система повертає помилку **Permission denied**[cite: 93]. [cite_start]Це відбувається тому, що механізм захисту Linux забороняє змінювати вміст файлу будь-кому, окрім власника або користувача з відповідними правами запису[cite: 111].

#### 3. Спроба видалення
[cite_start]Всупереч неможливості змінити вміст, видалення файлу командою `rm` проходить успішно (можливий запит на підтвердження `rm: remove write-protected regular file?`)[cite: 94]. 

**Чому це можливо?**
[cite_start]У Linux право на видалення файлу залежить не від прав самого файлу, а від **прав на директорію**, у якій він знаходиться. [cite_start]Оскільки домашній каталог належить звичайному користувачу і має права на запис, користувач може видалити будь-який запис у цій директорії, навіть якщо сам файл належить `root`.

### Висновок
Експеримент підтвердив, що:
* [cite_start]Права на **запис у файл** контролюють можливість зміни його вмісту[cite: 111].
* [cite_start]Права на **запис у каталог** контролюють можливість створення або видалення файлів у ньому, незалежно від того, хто є власником файлу.
Це критично важливий аспект безпеки: щоб захистити файл від видалення, потрібно обмежити права запису на рівні батьківського каталогу.

## Завдання 4

### Мета
[cite_start]Дослідити механізми ідентифікації користувачів у системі Linux та продемонструвати зв'язок між обліковим записом і групами доступу за допомогою команд `whoami` та `id`.

### Хід роботи та аналіз результатів

#### 1. Ідентифікація користувача
[cite_start]Програма викликає команду `whoami`, яка повертає логічне ім'я користувача, від імені якого запущено процес. Це дозволяє швидко перевірити, чи відбулося підвищення привілеїв (наприклад, до root).

#### 2. Аналіз групової належності
[cite_start]Виконання команди `id` надає більш детальну інформацію[cite: 98]:
* **UID (User ID):** Числовий ідентифікатор користувача.
* **GID (Group ID):** Основна група користувача.
* [cite_start]**Groups:** Список усіх додаткових груп, до яких належить користувач[cite: 98].



#### 3. Спостереження
[cite_start]Під час тестування команда `id` вивела не лише основну групу, а й перелік допоміжних груп (наприклад, `sudo`, `video`, `plugdev`), що підтверджує багатозадачність системи розмежування прав доступу в Linux[cite: 98]. Це демонструє, що права користувача складаються з сукупності прав усіх груп, до яких він входить.

### Висновок
[cite_start]Використання команд `whoami` та `id` у системному програмуванні дозволяє програмі усвідомлювати свій контекст безпеки[cite: 96, 97]. Це важливо для реалізації логіки доступу до ресурсів, де програма може заздалегідь перевірити, чи входить користувач до необхідної групи для виконання певної операції.

## Завдання 5

### Мета
[cite_start]Дослідити динаміку доступу до файлових ресурсів при зміні суб'єкта володіння та бітових масок дозволів за допомогою команд `chown` та `chmod`. [cite: 101]

### Хід роботи та результати

#### 1. Створення об'єкта
Програма ініціалізує тимчасовий файл, де поточний користувач є одночасно і власником, і творцем. [cite_start]На цьому етапі доступ до читання та запису є повним. [cite: 100]

#### 2. Ефект зміни власника (chown)
[cite_start]Після передачі прав власності користувачу `root` та встановлення прав `600` (`-rw-------`), звичайний користувач повністю втрачає доступ до файлу. 
* **Результат:** Спроби `fopen` повертають помилку `Permission denied`. [cite_start]Це доводить, що приналежність файлу суперкористувачу блокує будь-які дії інших суб'єктів, якщо це не дозволено маскою `others`. [cite: 102]

#### 3. Публічний доступ (chmod 666)
[cite_start]Коли права змінюються на `666` (`-rw-rw-rw-`), користувач знову отримує можливість читати та записувати файл, незважаючи на те, що власником залишається `root`. [cite: 102]

### Матриця доступу (результати експерименту)

| Сценарій                     | Власник | Права | Читання | Запис  |
|------------------------------|---------|-------|---------|--------|
| Початковий файл              | User    | 644   | Так     | Так    |
| Після chown root             | root    | 600   | Ні      | Ні     |
| Після chmod 666              | root    | 666   | Так     | Так    |

### Висновок
[cite_start]Експериментально підтверджено, що можливість виконання операцій читання та запису залежить від комбінації власника файлу та встановлених прав доступу. [cite: 102] [cite_start]Навіть якщо файл належить `root`, доступ може бути наданий звичайному користувачу через коректне налаштування бітів доступу для категорії `others`. [cite: 102]

## Завдання 6

### Мета
[cite_start]Проаналізувати структуру прав доступу в системних директоріях Linux (`/etc`, `/usr/bin`, `~`) та практично дослідити механізми захисту файлів від несанкціонованого читання, запису та виконання.

### Теоретичні відомості
[cite_start]У Linux файлова система базується на трьох типах прав: читання (r), запис (w) та виконання (x)[cite: 58].
* [cite_start]**Прямий запуск:** Для виконання файлу як програми необхідно мати встановлений біт `x`[cite: 58, 77].
* [cite_start]**Інтерпретаторний обхід:** Якщо файл є скриптом (наприклад, для Bash або Python), його можна виконати навіть без прав на виконання, якщо передати його як аргумент інтерпретатору (наприклад, `bash script.sh`)[cite: 59, 62]. [cite_start]У цьому випадку інтерпретатор лише читає вміст файлу, тому достатньо лише прав на читання[cite: 60, 78].

### Хід роботи та результати

#### 1. Огляд системних прав
[cite_start]Програма виконала `ls -l` для ключових шляхів[cite: 104]:
* **`~` (Home):** Зазвичай належить користувачу, права дозволяють повний доступ.
* **`/usr/bin`:** Містить виконувані файли системних утиліт. Власник — `root`, права зазвичай `755` (користувач може читати та виконувати, але не змінювати).
* **`/etc`:** Конфігураційні файли. Запис звичайним користувачам заборонено для забезпечення стабільності системи.

#### [cite_start]2. Спроби маніпуляцій [cite: 105]
* **Читання `/etc/shadow`:** Завершилося помилкою `Permission denied`. [cite_start]Це підтверджує, що критичні дані (хеші паролів) захищені від звичайних користувачів на рівні ядра[cite: 123].
* **Запис у `/usr/bin/ls`:** Спроба була заблокована. [cite_start]Це ілюструє захист бінарних файлів від модифікації (наприклад, впровадження шкідливого коду)[cite: 120].

#### [cite_start]3. Експеримент з обходом прав (Bypass) 
[cite_start]Я створив скрипт `noperm.sh` та видалив у нього біт виконання[cite: 68, 69].
* [cite_start]Спроба запуску через `./noperm.sh` призвела до відмови в доступі[cite: 74, 76].
* [cite_start]Спроба запуску через `bash noperm.sh` пройшла успішно[cite: 70, 72].
Це доводить, що права на виконання потрібні лише для того, щоб ядро могло ініціювати запуск файлу самостійно. [cite_start]Для скриптів ці права можна обійти, маючи права на читання[cite: 78].



### Висновок
Права доступу в Linux є багаторівневими. [cite_start]Хоча система надійно захищає бінарні файли та конфігурації від запису звичайними користувачами, важливо пам'ятати, що відсутність права на виконання (x) не гарантує неможливості запуску скрипта, якщо він залишається доступним для читання (r)[cite: 63, 66, 82].

## Завдання 1

### Мета
З'ясувати можливість доступу до вмісту файлу при відсутності встановлених прав доступу (`000`) та дослідити механізми перевірки дозволів у ядрі Linux.

### Теоретичне обґрунтування
[cite_start]Згідно з архітектурою UNIX, права доступу перевіряються в момент ініціалізації доступу до об'єкта (системний виклик `open`)[cite: 1, 58]. 
* Якщо файл вже відкритий, наступна зміна прав не впливає на поточні операції введення-виведення через активний файловий дескриптор.
* [cite_start]Суперкористувач (`root`) має можливість ігнорувати обмеження `rwx`, що дозволяє йому читати будь-які файли в системі.
* [cite_start]У випадках, коли права на виконання (x) відсутні, файл скрипта все одно можна "виконати", передавши його як аргумент інтерпретатору, якщо збережено права на читання (r)[cite: 59, 62, 78]. Проте при правах `000` цей метод не спрацює для звичайного користувача.

### Хід роботи та результати
Я реалізував експеримент, що демонструє два сценарії:
1. **Спроба повторного відкриття:** Після встановлення `chmod 000` виклик `open()` повертає помилку `EACCES`. Система блокує створення нового каналу зв'язку з файлом.
2. **Використання існуючого дескриптора:** Програма успішно зчитала дані через дескриптор, отриманий до зміни прав.



### Висновок
Прочитати файл із нульовими правами можливо у трьох основних випадках:
1. [cite_start]**Використання прав root**, який володіє повним доступом за замовчуванням[cite: 91].
2. **Наявність уже відкритого файлового дескриптора**, оскільки перевірка прав не проводиться при кожному виклику `read`.
3. **Наявність специфічних POSIX capabilities** (`CAP_DAC_OVERRIDE`), що дозволяють вибірково ігнорувати DAC-права.
Це підкреслює, що встановлення прав `000` не є абсолютною гарантією конфіденційності, якщо в системі є процеси, що вже працюють із файлом, або користувачі з високими привілеями.
